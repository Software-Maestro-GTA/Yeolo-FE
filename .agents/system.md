# Harness System-Wide Rules (하네스 공통 운영 규칙)

본 문서는 하네스 멀티 에이전트 시스템(Planner, Tester, Coder, Reviewer, Updater) 전체가 구동 및 협업 시 반드시 준수해야 하는 시스템 최우선 강제 규칙서입니다. 모든 에이전트는 개별 시스템 프롬프트 실행 전, 본 규칙을 최우선 컨텍스트로 주입하여 동작해야 합니다.

---

## 1. 프로젝트 및 환경 보존 규칙
- **패키지 매니저 준수**: 모노레포 환경이므로 반드시 `yarn`과 `yarn workspace`를 패키지 관리 및 스크립트 실행 도구로 사용하며, 임의로 `npm`이나 타 도구를 혼용하여 패키지를 설치하거나 명령을 실행하지 않습니다.
- **오케스트레이션 제어 파일 보호**: `.agents/` 디렉토리 하위의 설정 파일, 실행 훅 스크립트(`hooks/` 하위), 규칙 정의서(`skills/` 하위)를 임의로 훼손하거나 동의 없이 임의 수정하지 않습니다.

## 2. 에이전트별 분업 한계 준수 및 상호 권한 침해 금지 (Boundary Rule)
각 에이전트는 본인의 역할 외에 타 에이전트의 고유 쓰기 권한이 부여된 파일군을 수정할 수 없습니다:
- **Planner**: 기존 명세서를 수정할 수 없으며 오직 `progress.md` 기획만 담당합니다.
- **Tester**: 프로덕션 소스코드(각 패키지 하위 `src/`)를 수정할 수 없으며 오직 테스트 코드 작성만 담당합니다.
- **Coder**: 테스트 코드를 수정/삭제할 수 없으며 오직 프로덕션 소스코드 구현만 담당합니다.
- **Reviewer**: 소스코드나 테스트 코드를 임의로 수정할 수 없으며 오직 검증(`test.sh`) 및 이력 정리, 피드백만 담당합니다.
- **Updater**: 라이브 파이프라인 외부에서 작동하며 오직 에이전트 프롬프트, 셸 훅, 스킬 지침서만 수정합니다.

## 3. TDD 파이프라인 및 상태 무결성 준수 규칙
- **선제적 테스트 코드 작성 (Red Phase)**: `tester.md`가 실패하는 테스트 코드를 생성 및 확인하기 전에 `coder.md`가 먼저 실제 구현 코드를 개발하는 행위를 금지합니다.
- **테스트 결과의 객체성 신뢰**: 에이전트 자체의 추론에 의존하여 통과 여부를 임의 판단하지 않고, 실제 테스트 러너 실행 명령어의 exit code 결과(`0`이면 성공, 이외 실패)를 기반으로만 검증 결과를 기록합니다.
- **테스트 수정 절대 금지 (Zero Test Modification Rule)**: `coder.md`는 테스트를 강제로 통과시키거나 컴파일 에러를 우회하기 위해 `tester.md`가 작성한 테스트 코드 파일을 임의로 변경하거나 조작할 수 없습니다. 테스트 코드 자체에 에러가 있다면 Coder는 작업을 즉시 중지하고 반려(Tester 단계로 롤백) 처리를 요청해야 합니다.
- **독점적 진행 원칙**: 한 번에 오직 하나의 태스크만 `"진행중"` 상태여야 합니다. 이전 태스크의 리뷰가 완전히 승인되어 `"완료"`로 갱신되기 전까지 다음 태스크로 건너뛰거나 동시에 여러 태스크의 파일들을 변경하지 않습니다.

## 4. 지침 스킬 강제 로드 (Skill Loading Rule)
에이전트는 본인의 개별 프롬프트에 명시된 필수 확장 스킬 지침서(`skills/<스킬명>/SKILL.md`)를 작업 수행 전 `view_file` 도구로 먼저 완벽히 독해(Parse)한 후 결과물을 작성해야 합니다.

## 5. 로깅 투명성 규칙
- **에러 로그 상세화**: 빌드 에러나 테스트 실패가 발생했을 때 이를 숨기지 않습니다. 터미널 표준 에러 출력(stderr) 전체를 `log.md`에 가감 없이 정확히 기입하여 디버깅 피드백 컨텍스트로 제공합니다.

## 6. 모노레포 공통 아키텍처 보존 규칙 (Common Architecture Rule)
- **공통 API 및 전역 상태(`@yeolo/common`) 재사용 의무**:
  - 백엔드 REST/GraphQL API 호출 함수(`common/src/api/`), API 에러 클래스(`ApiError`), DTO 타입 및 Zustand 전역 상태 스토어(`common/src/store/`)는 특정 패키지(`app` 또는 `web`)에 파편화하여 구현하지 않고, 반드시 **`packages/common/` 하위에 작성하여 공유 및 재사용**합니다.
- **UI 컴포넌트 독립 모듈화 규칙**:
  - 화면(Screen/Page) 내에서 재사용되거나 독립된 역할을 수행하는 UI 요소(네비게이션 바, 플로팅 버튼, 분석 데이터 뷰 등)는 Screen 파일 내 인라인 작성을 금지하고, 반드시 **`components/` 하위 전용 파일로 독립 캡슐화**하여 구현합니다.
